## 결정과 이유

### 차트 도구는 Recharts

`02-tech-stack.md`에 Recharts로 정해 두었지만, 설치 전에 "왜 Recharts인가"를 다시 정리했다. 질문을 둘로 나누면 답이 분명해진다.

1. **왜 라이브러리를 쓰나 (SVG를 직접 그리지 않고)**: "인구 8,500명은 세로로 몇 px인가"(좌표 변환), "눈금을 몇 단위로 나눌까"(눈금 계산)를 직접 만들지 않으려고. 성능이 아니라 **만드는 시간**의 문제다.
2. **라이브러리 중 왜 Recharts인가**: React 전용이라 차트를 JSX 컴포넌트로 쓴다. `data` props만 바꾸면 React가 다시 그린다. 지금까지 `PlaceList`, `PlaceDetail`을 만든 방식과 같다.

|                       | Recharts                                        | Chart.js                                                                                                      |
| --------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| 그리는 방식           | SVG. 점·선이 각각 `<circle>`, `<path>` DOM 요소 | `<canvas>` 하나에 픽셀로 칠함                                                                                 |
| 쓰는 방식             | JSX 컴포넌트 (`<Line dataKey="..." />`)         | 프레임워크와 상관없는 JS. `new Chart(canvas, 설정)`. React에서는 `useRef`·`useEffect`로 직접 만들고 지워야 함 |
| 꾸미기                | 요소마다 CSS 변수·토큰을 넣기 쉬움              | 정해진 옵션 안에서만. 점 하나하나를 CSS로 다룰 수 없음                                                        |
| 데이터가 아주 많을 때 | DOM 요소가 수천 개 이상이면 느려짐              | 빠름 (실시간 시세, 모니터링 대시보드에 맞음)                                                                  |
| 접근성                | 요소가 DOM에 있음                               | 스크린리더에게는 그림 한 장이라 설명을 따로 붙여야 함                                                         |

**결론**: 점이 13개라 속도 차이는 없다. 그래서 속도가 아니라 React 방식과 맞고 토큰 색을 넣기 쉬운 Recharts를 골랐다. 대신 번들 크기가 늘어나는 비용이 있다. 면접에서는 "DOM 요소로 그리는 방식이 꾸미기 쉬움과 데이터가 많을 때 느림을 같이 만든다"는 한 문장으로 두 도구의 차이를 설명할 수 있다.

`pnpm add recharts`로 3.10.1을 설치했다. 설치 중 나온 "Ignored build scripts" 경고는 Recharts가 아니라 지도 변환용 `mapshaper`의 하위 패키지(`better-sqlite3` 등)에서 나온 것이다. pnpm은 허락하지 않은 패키지의 설치 스크립트를 실행하지 않는다.

### `ForecastCard`에 `'use client'`를 따로 적지 않는다

- Recharts는 브라우저에서 크기를 재고 마우스 이벤트를 다뤄서 클라이언트 컴포넌트에서만 동작한다.
- Next 문서(`05-server-and-client-components.md`)에 "`'use client'`가 붙은 파일이 **import하는 모듈과 직접 렌더링하는 컴포넌트**는 모두 클라이언트 번들에 들어간다"고 되어 있다. 기준은 "누가 부르나"가 아니라 **import 연결**이다.

```
floating-panel.tsx  ('use client')
  └ import PlaceDetail      (지시어 없음 → 클라이언트)
      └ import ForecastCard (지시어 없음 → 클라이언트)
```

- 그래서 지금은 적지 않아도 된다. 다만 나중에 `ForecastCard`를 서버 컴포넌트(예: `app/page.tsx`)에서 바로 import하면 서버 컴포넌트가 되어 Recharts가 동작하지 않는다.

### props는 `place` 하나, 그래프 데이터는 컴포넌트 안에서 만든다

- 그래프에는 예측 12칸(`place.forecast`)과 첫 점인 지금 값(`place.measuredAt`, `place.population`, `place.level`)이 둘 다 필요하다. 둘 다 `place` 안에 있어서 `PlaceDetail`처럼 `{ place }: ForecastCardProps`로 받는다.
- `Forecast` 한 칸을 props로 받으면 점 하나밖에 못 그린다.

### 13칸 배열: 지금 값을 예측 칸과 같은 모양으로 만들어 맨 앞에

```ts
const currentData: Forecast = {
  time: place.measuredAt,
  level: place.level,
  min: place.population.min,
  max: place.population.max,
};
const forecastData = [currentData, ...place.forecast];
const chartData = forecastData.map((item) => ({
  ...item,
  range: [item.min, item.max], // 띠: 아래 끝과 위 끝
  population: (item.min + item.max) / 2, // 선: 띠의 가운데
}));
```

- Recharts는 `data` 배열 하나를 받고, **배열의 한 칸이 가로축의 한 자리**다. 그래서 "지금" 1칸 + 예측 12칸을 배열 하나로 합친다. 지금 값을 `Forecast`와 같은 모양으로 만들어야 같은 선 위에 그릴 수 있다. `: Forecast` 타입을 적어 두면 필드를 빠뜨렸을 때 바로 알 수 있다.
- `<Area>`, `<Line>`은 배열을 따로 받지 않고, 판(`ComposedChart`)에 넘긴 배열의 각 칸에서 `dataKey` 이름의 필드를 **읽기만** 한다. 그래서 `map`은 JSX 안이 아니라 `return` 위에서 한 번 돌려 `range`, `population` 필드를 더한다.
- `<Area>`는 보통 0부터 값까지 칠하지만, 값이 `[min, max]` 두 개짜리 배열이면 **그 사이만** 칠한다. 서울시 인구가 원래 범위라서, 선만 그리면 범위라는 정보가 사라진다.
- 선은 높이가 하나만 필요해서 `(min + max) / 2`로 띠 한가운데를 지나게 했다.
- 배열이 두 개다. `forecastData`(원래 `Forecast` 모양)는 요약 문장 함수가, `chartData`(그래프용 필드를 더한 것)는 차트가 쓴다. 요약 문장 함수의 타입이 `Forecast[]`라서 원래 모양을 넘긴다.

### 판은 `ComposedChart`, 크기는 `responsive`

- `LineChart`는 선만 그리는 판이고, `ComposedChart`는 이름처럼 `Line`과 `Area`를 섞어 그릴 수 있다.
- `responsive` + `style={{ width: '100%', height: 214 }}`로 부모 너비에 맞춰 늘어난다. Recharts 3에 새로 생긴 방법이고, 예전에는 `<ResponsiveContainer>`로 감쌌다.

### 가로축: "지금"은 `value`로 판단하고, 3시간 간격으로

```tsx
<XAxis
  dataKey="time"
  axisLine={false}
  tickLine={false}
  interval={2}
  tickFormatter={(value) =>
    value === place.measuredAt ? '지금' : formatHour(value)
  }
  tick={{ fontSize: 10, fill: 'var(--color-text-subtle)' }}
/>
```

- `tickFormatter`는 Recharts가 눈금마다 불러 주는 함수다. 첫 인자 `value`에 그 칸의 `time`이 들어오고, 함수가 돌려준 글자가 라벨이 된다.
- **"지금"을 `index === 0`으로 판단하면 안 된다.** 둘째 인자 `index`는 데이터 13칸의 순서가 아니라 **숨기고 남은 눈금 중의 순서**다(`CartesianAxis.js`에서 숨기고 남은 `finalTicks`에 번호를 매긴다). 첫 칸 라벨이 숨겨지면 `index === 0`이 1시 눈금이 되어 1시를 "지금"이라고 보여 준다. 첫 칸의 `time`은 `place.measuredAt`을 그대로 넣었으니 `value`로 비교하면 정확하다.
- `interval={2}`: 두 칸 건너 하나씩, 즉 3시간 간격이다. 13칸이라 0, 3, 6, 9, 12번째가 보여서 "지금"과 마지막 칸이 둘 다 들어간다. 도안도 "지금, 17시, 20시, 23시, 2시"로 3시간 간격이다. 이 값을 넣은 이유는 아래 "문제와 해결"에 있다.
- 가로축 선(`axisLine`)과 눈금 표시(`tickLine`)는 도안에 없어서 껐다. 맨 아래 배경 가로선이 바닥선 역할을 한다.

### 세로축: 1만 미만은 숫자, 1만 이상은 "만"

```tsx
tickFormatter={(value: number) =>
  value < 10000
    ? value.toLocaleString('ko-KR')
    : `${Number((value / 10000).toFixed(1))}만`
}
```

- 세로축은 `dataKey`가 없다. Recharts가 `range`, `population` 값의 범위를 보고 `0, 6000, 12000, …`처럼 **보기 좋은 눈금 숫자를 직접 계산**해서 `value`로 넘긴다. 쓰는 모양은 가로축과 같다.
- `toFixed(1)`은 항상 소수점 한 자리 문자열이라 `1.0만`, `2.0만`이 된다. Recharts는 눈금을 딱 떨어지는 수로 고르는 경향이 있어서 자주 나온다. `Number('2.0')`은 `2`라서 한 번 감싸면 `.0`이 사라진다.
- 기준을 1만으로 둔 이유는 08의 `formatPopulation`과 같다. 인구가 적은 장소는 눈금이 전부 1만 아래(`0, 400, 800`)라 "만"으로 통일하면 `0.04만`이 된다. 대신 `0, 6,000, 1.2만, 1.8만`처럼 한 축 안에 표기가 섞일 수 있다는 걸 알고 그대로 두었다.
- 세로축은 0부터 시작한다. Recharts 기본값이고, 도안 예시는 0.2만부터지만 따로 바꾸지 않았다.

### 축 글자 크기와 색은 `tick` 객체로

- `tick={{ fontSize, fill }}`의 값은 라벨 `<text>` 태그의 **속성**으로 그대로 들어간다. Recharts가 기본값(`fill: '#666'` 등) **뒤에** 펼쳐서 기본값을 이긴다.
- 그래서 색은 Tailwind 클래스 이름(`text-subtle`)이 아니라 **CSS 변수**(`'var(--color-text-subtle)'`)로 적는다. Tailwind는 `className`에 적힌 클래스 이름만 CSS로 바꾸고, 속성 값의 글자는 건드리지 않는다. `fill="text-faint"`라는 색은 없어서 무시된다.
- `className`으로 하면 축 전체를 감싸는 `<g>`에 붙는다. 글자 크기는 물려받아 적용되지만, 색은 안 바뀐다. 아래 "새로 배운 것"에 정리했다.
- 도안은 9px인데 읽기 어려워서 10px로 했다. 가로축은 `text-subtle`, 세로축은 한 단계 옅은 `text-faint`로 도안 색을 따랐다.

### 차트 색은 도안 값, 이름은 지금 있는 토큰으로

| 요소        | 도안                  | 넣은 값                                                                |
| ----------- | --------------------- | ---------------------------------------------------------------------- |
| 배경 가로선 | `#EEEBE6`             | `CartesianGrid vertical={false} stroke="var(--color-skeleton)"`        |
| 띠          | `#E8E4DE`, 투명도 0.8 | `Area stroke="none" fill="var(--color-border-soft)" fillOpacity={0.8}` |
| 선          | `#1F1F1F`, 두께 1.4   | `Line stroke="var(--color-foreground)" strokeWidth={1.4}`              |
| "내일" 점선 | `#B5AFA7`, 3px 간격   | `ReferenceLine stroke="var(--color-map-line)" strokeDasharray="3 3"`   |

- 배경 가로선과 띠 색을 가리키는 semantic 토큰이 각각 `skeleton`(원래 로딩 화면용), `border-soft`(원래 테두리용)뿐이라 그 이름을 빌려 썼다. MVP 이후 `tokens.md`에 `--chart-grid`, `--chart-band` 같은 차트용 이름을 만들어 정리할 수 있다.
- `<Area>`의 기본 투명도는 0.6이라 `fillOpacity`를 적지 않으면 도안보다 연하다. 테두리(`stroke`)를 없애야 띠가 "면"으로 보인다.
- `CartesianGrid`는 가로축 눈금마다 세로선도 긋는다. 처음에 이 세로선이 "지금"을 뜻하는 선이라고 생각했는데, 실제로는 라벨이 찍힌 자리일 뿐이라 `vertical={false}`로 껐다. 도안에도 세로 격자선은 없다.

### 양 끝 여백은 없앤다 (`padding` 대신 `margin`)

- "지금" 점이 세로축에 붙어 보여서 처음에는 `XAxis`에 `padding={{ left: 12, right: 12 }}`를 줬다. 그러자 띠가 갑자기 시작하는 것처럼 보였다. `padding`은 그래프 영역 **안에서** 점들을 안쪽으로 밀어서, 축 끝까지 그려지는 배경 가로선만 12px 먼저 나와 있고 띠는 첫 칸부터 시작하기 때문이다. 지금보다 왼쪽(과거)은 데이터가 없어서 띠를 채울 수도 없다.
- 도안 HTML 좌표를 보니 배경 가로선과 띠가 같은 x에서 시작하고 같은 x에서 끝났다. 도안에는 양 끝 여백이 없다. "점이 세로축에 붙어 보이던" 원래 문제는 세로축 선 때문이었고, `axisLine={false}`로 선을 지운 뒤에는 붙을 선이 없다. 그래서 `padding`을 지웠다.
- 대신 오른쪽 끝 라벨이 잘려서 `ComposedChart`에 `margin={{ right: 12 }}`를 줬다. `margin`은 그래프 영역 **자체**를 줄여서 가로선·띠·점이 같이 끝나고, 그 바깥에 글자 자리만 생긴다.

### 점: 지금은 흰색으로 크게, 예측은 그 시각 혼잡도 색으로

```tsx
<Line
  dataKey="population"
  stroke="var(--color-foreground)"
  strokeWidth={1.4}
  dot={(props) => (
    <circle
      cx={props.cx}
      cy={props.cy}
      r={props.index === 0 ? 4.5 : 3.2}
      fill={
        props.index === 0
          ? 'var(--color-surface-white)'
          : `var(--color-congestion-${getBadgeVariant(props.payload.level)})`
      }
      stroke="var(--color-foreground)"
      strokeWidth={props.index === 0 ? 1.4 : 0.9}
    />
  )}
/>
```

- `dot`에 함수를 넘기면 Recharts는 기본 점을 그리지 않고, 점마다 이 함수를 불러 **돌려받은 SVG 태그를 그 자리에 그린다.** 그래서 점을 직접 `<circle>`로 만들어 돌려줘야 한다. 차트 전체가 `<svg>` 안이라 `<div>`는 안 된다.
- Recharts가 넘겨주는 값(`Dots.js`에서 확인): `cx`, `cy`(계산해 둔 점 위치), `index`(데이터 순서), `payload`(`chartData`의 그 칸 전체). 혼잡도는 `props`에 바로 있지 않고 **`props.payload.level`** 에 있다. `chartData`를 만들 때 `...item`으로 `level`을 복사해 뒀기 때문이다. `place.level`을 쓰면 13개 점이 모두 지금 혼잡도 색이 된다.
- 여기 `index`는 가로축 `tickFormatter`의 `index`와 달리 **데이터 순서 그대로**라 `index === 0`으로 "지금"을 고를 수 있다.
- 색 토큰 이름의 끝(`free`, `normal`, …)이 08에서 만든 `getBadgeVariant`가 돌려주는 값과 같아서, 함수를 새로 만들지 않고 템플릿 문자열로 `var(--color-congestion-normal)`을 만들었다. Tailwind 클래스와 달리 **CSS 변수 문자열은 이어 붙여도 된다.** 브라우저가 실행 중에 그 이름의 변수를 찾기 때문이다.
- "지금" 점을 흰색으로 둔 이유: 나머지 12개는 서울시 **예측값**이라 예측 혼잡도 색을 칠하고, "지금"은 실제로 잰 값이라 색으로 구분한다. 지금 혼잡도는 바로 위 배지에 이미 있다.
- `props.payload`는 Recharts 타입에서 `any`라서 `payload.levle` 같은 오타를 타입 검사가 잡지 못한다. 이 부분을 고칠 때는 눈으로 한 번 더 확인한다.

### 범례는 견본이 붙은 한 줄

```tsx
<p className="flex items-center gap-3 text-xs text-muted-foreground">
  <span className="flex items-center gap-1">
    <span className="flex gap-px" aria-hidden>
      <span className="size-1.5 rounded-full border border-foreground bg-congestion-free" />
      <span className="size-1.5 rounded-full border border-foreground bg-congestion-normal" />
      <span className="size-1.5 rounded-full border border-foreground bg-congestion-busy" />
    </span>
    그 시각 예측 혼잡도
  </span>
  <span className="flex items-center gap-1">
    <span className="h-2 w-3 bg-border-soft/80" aria-hidden />
    예측 인구 범위
  </span>
</p>
```

- 처음 문구 "점 색 = 해당 시각 혼잡도"는 흰 "지금" 점과 맞지 않고, 띠 설명도 없었다. 도안 문구 "점 색 = 그 시각 **예측** 혼잡도 · 회색 띠 = 예측 인구 범위"를 쓰면 "예측"이라는 단어 덕분에 흰 점이 예외가 아니라 "이건 예측이 아니다"라는 표시가 된다.
- 이 문구를 한 줄로 쓰면 읽기 어려워서 두 줄로 해 봤다가, "점 색 =", "회색 띠 =" 글자를 **작은 견본**(차트와 같은 모양의 빈 `<span>`)으로 바꿔 한 줄에 넣었다. 견본을 보고 차트와 바로 짝을 지을 수 있다.
- 견본과 글자 사이는 `gap-1`(4px), 두 항목 사이는 `gap-3`(12px)으로 다르게 줘서 짝이 보이게 했다. 견본은 장식이라 `aria-hidden`으로 스크린리더가 건너뛴다. 띠 견본의 `/80`은 차트의 `fillOpacity={0.8}`과 맞춘 투명도다.
- 위치는 도안처럼 왼쪽이다. 패널의 다른 줄이 모두 같은 왼쪽 선에서 시작해서, 범례만 오른쪽에 가면 그 선이 깨진다.

### "내일"은 가로축 라벨이 아니라 점선 위에

```tsx

  (data) => data.time.split(' ')[0] !== place.measuredAt.split(' ')[0],
);

{
  tomorrow && (
    <ReferenceLine
      x={tomorrow.time}

      strokeDasharray="3 3"
      label={{

        position: 'insideTopLeft',

        fill: 'var(--color-text-subtle)',

    />
  );
}
```

- 처음에는 가로축 라벨에 "내일 2시"처럼 붙였다. 점선을 넣으면서 "내일"을 어디에 둘지 다시 정했다. 점선만 있고 글자가 없으면 "거기에 뭐가 있는 것처럼" 느껴져서, 도안처럼 점선 위에 "내일"을 적고 가로축은 시각만 보여 주기로 했다.
- 그런데 요약 문장("내일 3시에 한산해요")에는 점선이 없어서 "내일"이 계속 필요하다. 그래서 시각 변환을 둘로 나눴다.

```ts
// '2026-11-10 03:00' → '3시'          (가로축)
export function formatHour(time: string): string { ... }

// 날짜가 다르면 '내일 '을 붙이고 나머지는 formatHour에 맡김 (요약 문장)
export function formatTime(currentTime: string, targetTime: string): string { ... }
```

시 부분을 꺼내는 코드는 `formatHour` 한 곳에만 있다.

- "내일"인지는 기기 시계(`new Date()`)가 아니라 **데이터의 기준 시각** 날짜와 비교한다. 예측 12칸은 서울시가 기준 시각부터 계산한 값이고, 앱은 캐시 때문에 23:55 기준 데이터를 다음 날 00:03에 보여 줄 수 있다. 기기 시계로 비교하면 그때 내일 2시가 "2시"로 보인다. 데이터와 비교하면 같은 배열에 언제나 같은 결과가 나와서 확인하기도 쉽다. (Cache Components에서는 서버에서 미리 그리는 부분에서 `new Date()`를 부르면 빌드 오류가 나는 제약도 있다.)
- 0시 반에 받은 데이터처럼 12시간 안에 날짜가 안 바뀌면 `tomorrow`가 `undefined`라 `tomorrow && (...)`로 점선을 그리지 않는다.
- `position: 'insideTopLeft'`는 선 위쪽 끝의 오른쪽 옆에 글자를 놓는다. 도안도 점선 오른쪽 위에 "내일"이 있다.
- `<ReferenceLine>`은 `<Line>`보다 위(앞)에 적었다. 이유는 아래 "Recharts 3의 그리기 순서"에 있다.

### 요약 문장은 `lib/congestion.ts`의 `getForecastSummary`

### 요약 문장 규칙은 세 번 바뀌었다

**① 처음 달라지는 칸 (`e9f33f9`)**

```ts
const changedForecast = forecastData.find((d) => d.level !== current.level);
// 없으면 '당분간은 지금과 비슷해요'
// 있으면 점수 비교로 '○시부터 한산해져요' / '○시부터 혼잡해져요'
```

- 문구는 사용자가 "약간 붐빔" 같은 단계 이름을 잘 모를 수 있어서 일상어("한산해져요 / 혼잡해져요")로 정했다. 단계 이름을 그대로 쓰면 "여유로워져요"가 붐빔 → 약간 붐빔에도 나오는 틀린 말이 된다.
- 문제: 서울역(보통 → 18시만 약간 붐빔 → 19시부터 계속 여유)이 "18시부터 혼잡해져요"로 나왔다. 그래프는 계속 내려가는데 문장은 붐빈다고 말했다. 그때 121곳 중 102곳이 "혼잡해져요"였다. 퇴근 시간에 한 시간만 붐비는 장소가 다 걸렸다.

**② 2시간 이어지는 단계** (중간 단계, 커밋 안 함)

- "현재가 여유면 혼잡만, 붐빔이면 한산만 알려 주고 나머지는 비슷"하는 안도 생각했다. 하지만 단계가 넷이라 가운데(보통, 약간 붐빔)에 있는 장소가 많고, 서울역은 "보통"이라 "비슷해요"가 나와 더 틀린 안내가 된다. 진짜 문제는 방향이 아니라 **한 시간짜리 변화도 센다**는 점이었다.
- 그래서 "처음 바뀐 단계가 다음 칸에도 같을 때만" 변화로 봤다. 서울역은 "19시부터 한산해져요"가 됐다.
- 남은 문제: 단계 이름이 정확히 같은지만 봐서, 대림역(여유 → 붐빔, 약간 붐빔, 붐빔 …)처럼 비슷한 단계끼리 오가면 끊긴 것으로 봤다. 실제로는 19시부터 계속 붐비는데 "21시부터"가 나왔다.

**③ 같은 방향이 2시간 이어지는 첫 칸 (`d90ad87`)**

```ts
const currentScore = levelToScore(forecastData[0].level);
// 지금보다 붐비면 1, 같으면 0, 한산하면 -1
const getDirection = (level: CongestLevel) =>
  Math.sign(levelToScore(level) - currentScore);

const changedForecast = forecastData.find((d, i) => {
  const next = forecastData[i + 1];
  if (!next) return false; // 마지막 칸은 이어지는지 확인할 수 없어서 제외
  const direction = getDirection(d.level);
  return direction !== 0 && getDirection(next.level) === direction;
});
```

- 단계 점수에서 지금 점수를 빼고 `Math.sign`으로 **부호만** 남긴다. 붐빔(+3)과 약간 붐빔(+2)이 둘 다 `1`("지금보다 붐빔")로 묶여서, 비슷한 단계끼리 오가도 이어진 것으로 본다. 대림역과 삼각지역이 "19시"로 맞게 나왔다.
- `find` 콜백의 둘째 인자 `i`로 다음 칸(`forecastData[i + 1]`)을 본다. 마지막 칸은 다음 칸이 없어서 먼저 `return false`로 건너뛴다. 이렇게 걸러 두면 그 아래에서 TypeScript도 `next`가 항상 있다고 안다. 12시간 뒤 마지막 한 시간이라 놓쳐도 영향이 작다.
- 이 방향 로직(`getDirection`과 `find` 조건)은 사용자가 원리를 이해한 뒤 Claude에게 작성을 맡긴 부분이다. `sort` 비교 함수가 음수/0/양수로 앞뒤를 정하는 것과 같은 생각이다. 다른 점은 `sort`는 부호만 보지만, 여기서는 두 칸의 방향을 `===`로 비교해야 해서 `Math.sign`으로 `-1 / 0 / 1` 셋 중 하나로 맞춘다는 것이다.

### 문장은 "변화"가 아니라 "그 시각의 상태"로

```ts
// 혼잡도 단계 -> 예측 요약 문구
const LEVEL_SUMMARY_TEXT: Record<CongestLevel, string> = {
  여유: '한산해요',
  보통: '사람이 조금 있어요',
  '약간 붐빔': '약간 붐벼요',
  붐빔: '붐벼요',
};

return `${formatTime(currentTime, changedForecast.time)}에 ${LEVEL_SUMMARY_TEXT[changedForecast.level]}`;
```

- 규칙 ③을 넣자 잠실한강공원이 "20시부터 혼잡해져요"로 나왔다. 데이터를 보니 지금 여유 2,000~2,500명 → 20시 보통 **1,500~2,000명**이었다. **인구는 줄어드는데 혼잡도는 올라간다.** 서울시는 예측 인구와 예측 혼잡도를 따로 계산해서 주고, 둘이 항상 같은 방향으로 움직이지 않는다. 우리 그래프는 선 높이가 인구, 점 색이 혼잡도라서 선은 내려가는데 문장은 붐빈다고 말하는 모순처럼 보였다.
- "사람 적은 곳을 찾는 서비스니 한산해지는 것만 알려 주자"는 안도 생각했다. 하지만 사람을 피하려는 사용자에게 가장 필요한 정보는 "곧 붐빈다"는 경고라서 혼잡 안내는 남겼다.
- "사람이 몰려요"는 인구가 는다는 뜻이라 잠실한강공원에서 그래프와 정면으로 부딪힌다. 그래서 문장이 인구 변화가 아니라 **그 시각의 혼잡도 상태**만 말하게 바꿨다. "20시에 사람이 조금 있어요"는 인구가 줄었든 늘었든 참이고, 언제나 그 시각의 점 색과 맞는다. 한산 쪽에도 같은 규칙이 적용돼서 한산/혼잡 `if` 분기가 없어지고 표 하나로 정리됐다.
- 조사는 "부터"가 아니라 **"에"** 다. 2시간만 이어지고 바로 바뀌는 경우도 있어서 "부터"는 계속 그 상태일 것처럼 들린다. 그리고 "부터"는 "한산해져요" 같은 변화 동사와, "에"는 "한산해요" 같은 상태와 어울린다.
- 마지막 단계는 "사람이 많아요" 대신 **"붐벼요"** 로 했다. "약간 붐벼요 → 붐벼요"로 이어져서 단계 차이가 분명하고, 바로 위 배지의 `약간 붐빔`, `붐빔`과 같은 단어라 연결이 쉽다.
- 단계 → 문구 표는 08의 `LEVEL_BADGE_VARIANT`와 같은 `Record<CongestLevel, …>` 모양이라 단계 하나를 빠뜨리면 타입 오류가 난다. 두 표를 나란히 둬서 "단계를 다른 값으로 바꾸는 표"를 한곳에서 찾을 수 있다.

### 가로축은 "지금부터 12시간" 칸 축 그대로

- 날씨 앱처럼 시작점이 매번 바뀌는 대신, "시간대별 방문자" 그래프처럼 0~24시 고정 축에 현재 시각 세로선을 긋는 안도 생각했다.
- 고정 축은 **지난 기록을 시간대별로 평균 낸** 데이터에 맞다. 서울시 API는 지금 값 + 앞으로 12시간 예측만 줘서, 어떤 고정 범위를 잡아도 시각에 따라 빈 곳이나 잘리는 곳이 생긴다. "지금부터 앞으로" 데이터는 축이 지금과 같이 움직이는 게 일반적이다.
- 대신 첫 라벨을 "지금"으로, 그래프의 핵심은 요약 문장으로 먼저 알려 준다. 서울시 데이터를 직접 쌓아 시간대별 평균을 만들 수 있게 되면 고정 축 그래프를 **추가**하는 건 좋은 개선이다.

## 문제와 해결

### 배열을 펼치는 위치가 틀려서 13칸이 아니라 2칸

- **원인**: `[...[currentData], place.forecast]`로 썼다. `...`이 객체 쪽에 붙고 예측 배열에는 없어서, 둘째 칸에 예측 12칸이 **배열 통째로** 들어갔다.
- **해결**: `...`은 펼칠 배열 쪽에 붙인다. `[currentData, ...place.forecast]`.
- 타입 검사가 못 잡은 이유: `data`가 "아무 모양이나 든 배열"을 받아서 `[객체, 배열]`도 문제없는 배열이다. 작은 배열로 직접 실행해 길이를 보고 찾았다.

### 요약 문장을 연결하자 그래프가 사라짐

- **원인**: 요약 문장 함수에 `forecastData`를 넣으면서 `<ComposedChart data>`까지 `forecastData`로 바뀌었다. `forecastData`에는 `range`, `population` 필드가 없어서 `<Area>`, `<Line>`이 읽을 값이 없었다. `'chartData' is assigned a value but never used` lint 경고가 같은 원인을 가리키고 있었다.
- **해결**: 차트는 `chartData`, 문장 함수는 `forecastData`로 되돌렸다.

### 화살표 함수가 아무것도 돌려주지 않음 (`tickFormatter`, `dot` 두 번)

- **원인**: `(value) => { value === … ? '지금' : … }`처럼 `=>` 뒤에 `{ }`를 쓰고 `return`을 안 적었다. `Type '(value: any) => void' is not assignable to type '... => string'` 오류가 났다. `dot`에서도 `{ <circle … />; }`로 같은 실수를 했고, 처음에는 `{ cx = …; cy = …; }`처럼 태그 없이 대입문을 나열해 문법 오류가 났다.
- **해결**: `{ }` 대신 `( )`로 감싸 값을 바로 돌려줬다. `{ }`는 함수 본문이라 `return`을 적어야 하고, `( )`는 안의 값 하나를 그대로 돌려준다.

### `formatTime`이 "시"만 돌려줌

- **원인**: `formatHour`를 만들고 `formatTime` 안에서 `formatHour(targetTime);`을 부르기만 하고 결과를 받지 않았다. 돌려받지 않은 값은 사라진다. 요약 문장이 "시부터 한산해져요"가 됐다. 결과를 안 쓰는 것도 문법상 맞는 코드라 타입 검사가 못 잡는다.
- **해결**: 결과를 `formattedTime`에 받아 `'내일 '` 뒤에 붙였다. `formatHour`가 이미 "시"를 붙여서 `return` 줄의 "시"는 뺐다(안 빼면 "3시시").

### `formatHour`로 바꾸다가 "지금" 조건까지 지움

- `tickFormatter`의 `formatTime(...)`을 `formatHour(value)`로 바꾸면서 삼항 연산자까지 지워 첫 눈금이 "15시"로 나왔다. 삼항 연산자는 두고 `:` 뒤만 바꿨다.

### 패딩을 지우자 "지금" 라벨이 사라짐

- **원인**: `XAxis`의 `interval` 기본값 `'preserveEnd'`는 마지막 눈금부터 거꾸로 돌며 겹치지 않는 라벨만 남기고, 마지막이 아닌 라벨은 **축 영역 밖으로 조금이라도 나가면 숨긴다**(`getTicks.js`의 `isVisible` 검사). 라벨은 점 아래 가운데에 놓인다. 패딩을 0으로 하자 "지금" 점이 축 맨 왼쪽 끝에 붙어 글자의 왼쪽 절반이 축 밖으로 나갔고, 그래서 숨겨졌다.
- **해결**: `interval={2}`. 숫자를 주면 자동 숨김 계산을 하지 않고 "N개 건너 하나씩" 보여 준다.
- **이어진 문제**: 숫자 `interval`은 `preserveEnd`의 "마지막 라벨은 안쪽으로 밀어서라도 보여 준다"도 꺼서, 맨 오른쪽 "5시"의 오른쪽 절반이 `<svg>` 밖으로 나가 잘렸다. `ComposedChart`의 `margin` 기본값은 사방 5px라 글자 반쪽(약 8px)이 들어갈 자리가 모자랐다. `margin={{ right: 12 }}`로 해결했다.

### `getForecastSummary`를 고치다 비교 대상과 인자가 바뀜

- 규칙 ②를 만들 때 다음 칸을 `currentLevel`과 비교했다(`next?.level === currentLevel`). 이건 "다음 칸이 **지금으로 돌아오는가**"라서, 걸러야 할 "잠깐 바뀌었다 돌아오는 칸"만 골랐다. 서울역이 "비슷해요"가 됐다. 비교 대상을 이 칸(`d.level`)으로 고쳤다.
- 같은 때 `current.level`을 `currentLevel`로 바꾸면서 `formatTime(current.time, …)`까지 `formatTime(currentLevel, …)`이 됐다. `'보통'`의 날짜 부분은 언제나 예측 날짜와 달라서 오늘 시각에도 "내일"이 붙었다. 둘 다 `string`이라(`CongestLevel`도 `string`의 한 종류) 타입 검사가 못 잡았다. 현재 시각을 `currentTime` 변수로 따로 뺐다.
- 둘 다 같은 로직으로 세 가지 데이터(한산해짐, 잠깐 붐빔, 혼잡해짐)를 돌려서 결과가 거꾸로 나오는 걸 보고 찾았다.

## 확인한 사실

- 요약 문장 규칙별 실제 데이터 121곳 결과 (규칙마다 받은 시각이 달라 같은 시점 비교는 아니다):
  - ① 처음 달라지는 칸 (11/9 낮): 혼잡해져요 102 · 한산해져요 11 · 비슷해요 8
  - ② 2시간 이어지는 단계 (11/9 저녁): 한산해져요 62 · 혼잡해져요 34 · 비슷해요 25
  - ③ 2시간 이어지는 방향 (같은 데이터): 한산해져요 61 · 혼잡해져요 37 · 비슷해요 23
  - ③ + 상태 문구 (그 뒤 다시 받은 데이터): 한산해요 43 · 비슷해요 49 · 사람이 조금 있어요 19 · 약간 붐벼요 8 · 붐벼요 2
- 서울시 예측 인구와 예측 혼잡도는 엇갈릴 수 있다. 잠실한강공원은 여유 2,000~2,500명 → 보통 1,500~2,000명이었다.
- 기준 시각과 첫 예측 사이는 1시간이 아니다. 기준 시각이 18:40이면 첫 예측은 20:00일 수 있다. 칸 축이라 이 간격도 다른 칸과 같은 폭으로 그려진다.
- Recharts 3은 `tickFormatter(value, index)`의 `index`가 보이는 눈금 중의 순서이고, `dot` 함수의 `index`는 데이터 순서다.
- Recharts 3은 JSX 순서가 아니라 요소마다 정해진 zIndex로 층을 나눠 그린다(`DefaultZIndexes.js`).

## 한계 (MVP 이후)

- **예측 인구와 혼잡도의 엇갈림**: 서울시 데이터의 특성이라 고칠 수 없다. 문장을 "그 시각의 상태"로 바꿔서 문장과 점 색은 항상 맞게 했지만, 선이 내려가는데 점 색이 진해지는 장면은 남는다. 면접에서 "왜 선은 내려가는데 붐빈다고 나오나요?"라는 질문에 이걸로 답한다.
- **칸 축의 간격 왜곡**: 가로축이 13칸을 같은 간격으로 놓는 범주형(category) 축이라, "지금"과 첫 예측 사이가 실제로 25분이든 1시간 20분이든 1시간 칸과 같은 폭이다. 가로축을 숫자(타임스탬프) 축으로 바꾸고 1시간 눈금을 직접 지정하면 정확해진다.
- **차트용 색 토큰 이름**: 배경선은 `skeleton`, 띠는 `border-soft`를 빌려 쓴다.

## 새로 배운 것

### Recharts의 기본 구조

| 컴포넌트         | 하는 일                                                             |
| ---------------- | ------------------------------------------------------------------- |
| `ComposedChart`  | 그래프 판. `data` 배열을 받는다. 배열의 한 칸 = 가로축의 한 자리    |
| `XAxis`, `YAxis` | 축. 좌표 변환과 눈금 계산을 자동으로 한다                           |
| `Area`, `Line`   | 실제로 그려지는 모양. `dataKey`로 "각 칸의 어느 필드를 쓸지" 정한다 |
| `CartesianGrid`  | 눈금 자리마다 배경선                                                |
| `ReferenceLine`  | 원하는 값 한 곳에 기준선 하나                                       |

- 데이터 모양이 먼저다. 그리기 전에 각 칸에 그래프가 읽을 필드(`range`, `population`)를 넣은 배열을 만든다.
- `tickFormatter`, `dot`처럼 함수를 넘기는 props는 **내가 부르지 않고 Recharts가 값마다 불러 준다.** 무엇을 넣어 주는지는 타입 정의(`types.d.ts`)나 코드(`Dots.js`, `CartesianAxis.js`)에서 확인한다.

### SVG 속성은 부모 CSS보다 약하지만, 상속보다는 강하다

```html
<g class="recharts-xAxis …">
  ← className은 여기 <text fill="#666">지금</text> ← tick 객체는 여기 속성으로
</g>
```

- `fill` 같은 CSS 속성은 **자식에게 자기 값이 없을 때만** 부모에게서 물려받는다. Recharts가 `<text fill="#666">`을 직접 적어 두어서, 부모 `<g>`에 준 색은 무시된다. 글자 크기는 `<text>`에 따로 적혀 있지 않아서 부모 `className`이 먹힌다. 그래서 "크기는 `className`으로 되는데 색은 안 된다."
- 부모가 아니라 `<text>`를 직접 겨냥하는 CSS(`className="[&_text]:fill-text-subtle"`)는 SVG 속성(`fill="#666"`)을 이긴다. CSS 규칙이 SVG 속성보다 우선순위가 높다.
- 가장 단순한 건 `tick={{ fontSize, fill }}`로 `<text>`에 직접 넘기는 것이다.

### Recharts 3의 그리기 순서는 zIndex

- 보통 SVG는 나중에 적은 태그가 위에 그려진다. Recharts 3은 요소마다 정해진 zIndex로 층을 나눈다: 배경 가로선 -100, 띠 100, 선·기준선 400, 축 500, 점 600, 라벨 2000. 같은 층 안에서만 JSX 순서를 따른다.
- 그래서 점은 언제나 점선 위다. 선과 점선은 둘 다 400이라 "기준선은 데이터 아래"가 되게 `<ReferenceLine>`을 `<Line>` 앞에 적었다.

### `XAxis`의 `padding`, `interval`과 `ComposedChart`의 `margin`

| prop                   | 하는 일                                                                                                       |
| ---------------------- | ------------------------------------------------------------------------------------------------------------- |
| `XAxis padding`        | 그래프 영역 **안에서** 첫/마지막 칸을 안쪽으로 민다. 축 끝까지 그려지는 배경선만 삐져나온다                   |
| `ComposedChart margin` | `<svg>` 테두리와 그래프 영역 사이 여백. 그래프 영역 **자체**를 줄인다. 기본 사방 5px                          |
| `XAxis interval`       | 기본 `'preserveEnd'`: 겹치거나 축 밖으로 나가는 라벨을 자동으로 숨김. 숫자 N: N개 건너 하나씩, 숨김 계산 없음 |

### Tailwind 클래스는 완성된 글자, CSS 변수는 이어 붙여도 된다

- Tailwind는 빌드할 때 코드에 **글자 그대로** 적힌 클래스만 만든다. `` `bg-congestion-${…}` ``는 안 된다.
- `` `var(--color-congestion-${…})` ``는 된다. CSS 변수는 브라우저가 실행 중에 이름으로 찾기 때문이다. SVG 속성이나 `style`에 넣는 값이 여기에 해당한다.

### 화살표 함수의 `{ }`와 `( )`

```ts
(v) => v * 2          // 식의 결과를 돌려줌
(v) => ({ a: v })     // 객체를 돌려줄 때는 ( )로 감쌈
(v) => { v * 2; }     // 본문. return이 없어서 undefined
(v) => { return v * 2; }
```

- JSX를 돌려줄 때도 `=> ( <circle … /> )`처럼 `( )`로 감싼다.
- 태그 뒤 **같은 줄**에 `{/* 주석 */}`을 붙이면 Prettier가 그 사이 공백을 지키려고 `{' '}`(빈칸 글자)를 넣는다. 주석은 태그 위 줄에 쓴다.

### `find`의 두 번째 인자와 `Math.sign`

- `arr.find((item, i) => …)`의 `i`는 지금 보고 있는 칸의 위치다. `arr[i + 1]`로 다음 칸을 볼 수 있고, 마지막 칸에서는 `undefined`다.
- `Math.sign(x)`는 부호만 돌려준다: 양수 `1`, 0 `0`, 음수 `-1`. 크기는 버리고 방향만 남겨서 "지금보다 붐빔"끼리 `===`로 묶을 수 있다.

### `'use client'` 경계는 import 연결로 정해진다

- `'use client'` 파일이 import하는 모듈은 지시어가 없어도 클라이언트 쪽에 들어간다. 같은 컴포넌트라도 서버 컴포넌트에서 바로 import하면 서버 컴포넌트가 된다.
